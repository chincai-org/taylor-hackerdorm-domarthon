### Decisions worth remembering

- **View switch and info chips are real radio groups** (`<input>` + `<label>`), shown
  and hidden with `body:has(#id:checked)` — no JS, and the arrow keys work natively.
- **Version selection is driven by the URL fragment.** Figure nodes link to a strip's
  id (`#s-<short>`); `:target` reveals that strip and, via an adjacent-sibling rule, its
  record. `main.js` only calls `preventDefault()` + `history.replaceState()` to stop the
  page jumping — verified that `replaceState` does update `:target` in Chromium.
- **Per-node selection styling is generated** into a small `<style>` block per page,
  setting custom properties (`--sel-ring`, `--sel-hit`, `--sel-edge`, `--sel-backdrop`,
  `--sel-row`) that the shared stylesheet consumes. This keeps one rule per node instead
  of four.
- JS-only controls (copy buttons, fork picker) are hidden until `main.js` sets
  `html.has-js`, so nothing inert is ever shown.

### Clicking a version was broken — `:target` is not re-evaluated on replaceState

Tested the interaction by clicking a node with Playwright on both sites:

```
LIVE  click he-07 → strip "REJECTED · he-07 load every skill at start", panel follows
MINE  click he-07 → hash became #s-he-07 but strip/panel/ring stayed on he-08
```

Root cause: my selection drove off `:target` alone, and the script only called
`history.replaceState`. **`:target` is not re-evaluated when the fragment is rewritten in
place after load** — an earlier one-off test had wrongly suggested it was, because it set
the fragment during initial script execution, before the first style resolution, so the
target element was simply computed for the first time.

Fix: `main.js` drives selection with an `is-open` class (mirroring a fragment present on
load), and the generated per-page rules accept either path:

```css
:is(body:not(:has(.selected-strip.is-open)):has(#s-X:target), body:has(#s-X.is-open)) …
```

The `:target` half switches off as soon as a strip is marked, so two records can never show.

Verified both ways afterwards:
- **JS on** — click he-07 then he-02: strip, record panel and ring all follow, exactly one
  of each visible. Identical readout to the live site.
- **JS off** — real anchor navigation still updates `:target`: he-07 → he-12 both switch,
  and the info chips (radios + `body:has(#chip-…:checked)`) still switch panels.

### The JS-off selection bug — one fragment cannot mean two things

`checks/nojs.mjs` (a JS-disabled context) caught a real defect: clicking "Full record ↓"
**silently reset the page to its default version**. The strip carried `id="s-<short>"` and
the figure's links targeted it, but "Full record" targeted `#record` — and `#record` matches
none of the generated `#s-*:target` rules, so every strip collapsed and the default came back.
The reference does not have this bug because its selection is React state and independent of
the fragment, so `#record` is free for it to use.

Fix: **moved the `s-<short>` id off the strip and onto the version's `<article class="rec">`.**
Now `#s-he-07` both *selects* the version and *scrolls* to its record, and "Full record ↓"
points at that same fragment, so it scrolls without clearing anything. Consequences:

- `main.js` keys selection off `strip.dataset.for` rather than `strip.id`, and the
  "Full record" `preventDefault` handler was deleted — the anchor is now a normal link.
- The `chosen()` rule became
  `:is(body:not(:has(.selected-strip.is-open)):has(#s-X:target), body:has(.selected-strip.is-open):has(.selected-strip[data-for="X"].is-open))`
  because the script's marker is on the strip but the fragment matches the record.
- The "nothing chosen yet" test moved from `.selected-strip:target` to `.rec:target`, so a
  stray `#record` correctly leaves the default on show.
- `.rec` gained `scroll-margin-block-start: 64px` so a targeted record clears the 52px bar.

Also investigated and **correctly rejected**: I first assumed the reference drove its
Tree|Stats switch and info chips from URL fragments, and added `:target` shadow rules plus
`p-*` / `view-*-a` anchors to match. Reading `ref/components/Panels.tsx` and
`TreeWorkspace.tsx` showed they are React buttons with `aria-pressed` — no such anchors exist
anywhere. All of that was reverted; the radio groups stay as they are.

### Clipboard icon buttons (replacing the text copy buttons)

User wanted the "copy" affordance to be the familiar clipboard glyph you get when copying
code, and — more importantly — to actually copy. The old buttons were text (`Copy`) and
the clipboard write silently did nothing when `navigator.clipboard` was unavailable, which
is a real bug on a plain `file://` page opened from the filesystem.

**Markup.** `build.mjs` gained a `copyButton(attributes, label)` helper emitting an M3 icon
button with **both** glyphs inline; CSS decides which one shows:

    <button type="button" class="icon-btn copy needs-js" data-copy="…"
            aria-label="Copy the command: …" title="…">
      <svg class="icon-copy">   …17×17 stroked clipboard…
      <svg class="icon-copied"> …tick…
    </button>

The clipboard glyph is `fill:none; stroke:currentColor` line art (16px drawn in a 24-unit
box) so it inherits the M3 on-surface colour at rest and turns `primary` (blue) on success.
It replaces two text buttons: the fork command in the tree panel, and each check-it command
in the record.

**Behaviour (**`main.js`**).** New `writeClipboard(text)` returns a boolean: try
`navigator.clipboard.writeText`, else fall back to an off-screen `<textarea>` +
`document.execCommand("copy")`. On success the button gets `is-copied` (blue tick, clipboard
glyph hidden), its `aria-label` becomes "Copied", and a sibling `.sr-only` `role="status"`
announces "Copied to clipboard". Reset after 1600ms. **The tick is not shown if the write
failed** — the affordance never lies about having copied.

**Icon-only accessibility.** Because there is no visible text now, the button carries both
`aria-label` and `title`, and the announced state lives in a `.sr-only` live region rather
than on the button (so a screen reader hears "Copied to clipboard" without refocusing).

**New check `checks/copy-fallback.mjs`:** deletes `navigator.clipboard` from the page before
load and asserts the `execCommand` path still shows the tick and announces success. Needed
because **Edge reports even `file://` as a secure context**, so the fallback never fires
naturally while testing locally.

Two test-only gotchas (not bugs in the deliverable): Chromium normalises clipboard newlines
to CRLF, so a direct string compare against the `<pre>` content fails; and
`document.querySelector("[data-fork-out]")` returns the *first* record's command, not the
one on show, so readability assertions must be scoped to the visible record.

Final state unchanged elsewhere: 0 contrast failures, 0 sub-12px text, 0 undersized tap
targets, 0 failing combinations out of 63, selection/chips/switch correct with JS both on
and off, and 0 copy buttons rendered when scripting is off (commands stay readable as
plain text).

### Copy control moved inside the command box

The fork block put its copy button *below* the command box while the check-it blocks put
it *inside* theirs — two different treatments for the same control. The user asked for the
fork one to match (`make the copy clipboard inside the black box`).

Confirmed what the reference does, because it is not consistent either: its `.checkit-cmd`
is a 318x42 flex row with a "Copy" text button at the inline end, while its `.np-block.fork`
is 346x249 with the button *below* the `<pre>`. So the reference's fork block is the odd
one out, and the check-it treatment is the one to copy.

**One shared box.** The two blocks now use a single `.cmd` class holding the layout
(`display:flex`, `align-items:center`, `gap:8px`, `padding:6px 6px 6px 12px`,
`border-radius: shape-sm`, sunken surface), with `.checkit-cmd` reduced to a top margin and
the fork block using `.cmd` alone. Markup changed in `build.mjs`:

    <div class="cmd">
      <pre data-fork-out="he-08">…</pre>
      <button class="icon-btn copy needs-js" …>…</button>
    </div>

**`data-fork-out` must stay on the `<pre>`, not the wrapper** — `main.js` does
`out.textContent = …` when the direction changes, and pointing it at the wrapper would
delete the button from the DOM on the first picker change. `checks/cmd-box.mjs` asserts the
button is a *sibling* of the command element and that exactly one survives a picker change.

**Measured result** (identical for both blocks, every width): box 44px tall, button 32x32,
4px from the inline end, 6px top and bottom. The fork box grows with the command (324x76
at sidebar widths, 596x44 when stacked, 256x108 at 360px). 100 assertions, 0 failures.

**Also switched the fork command from scroll to wrap.** `white-space: pre` + `overflow-x:
auto` hid most of the command behind a scrollbar in the 324px record column; the reference
wraps. Now `white-space: pre-wrap; overflow-wrap: normal`.

- A soft wrap inserts no characters, so the clipboard payload is byte-identical either way
  — verified, not assumed.
- `overflow-wrap: break-word` was tried first and **reverted**: it splits a token at the
  overflow point. At these content widths it happened to render the same, so the test that
  catches it needs a synthetic over-long token to fire at all — worth knowing, because a
  green test that can never go red is not evidence.
- A break *after a hyphen* is unavoidable: `--area` can end a line as `--` / `area`.
  Measured `word-break: keep-all`, `line-break: strict`, `break-spaces` and `overflow-wrap:
  anywhere` — all break in the same place. Only markup around each token would stop it.
  The check reports this as a `note`, not a failure, and only fails on a real word split.
- Consequence: the copy button now takes ~34px of the command's width (300 -> 266px), which
  is what pushes the fork command into wrapping at sidebar widths.

`checks/cmd-box.mjs` is new: box/button geometry at six widths, sibling relationship,
mid-word break detection, and command text integrity. `checks/sweep.mjs` no longer lists
command boxes as legitimate scrollers, so overflow inside one now fails the sweep.
`checks/shots.mjs` gained `9-fork-box`, `10-fork-copied` and `11-checkit-box`;
`checks/copy-fallback.mjs` now also writes `8-copy-done`. `shots/ref-fork.png` and
